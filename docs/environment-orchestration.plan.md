# Local Environment Orchestration — Implementation Contract

## Problem and Success Criteria
- A user/agent can say "backend on 3000, frontend on 5173, test login" and the system tops up from single-service control to an owned multi-service stack: discovery-proposed topology (never a hand-written manifest as adoption requirement) → `environment_up` in dependency order with honest per-service `starting/ready/failed/skipped` → `verification_run`-against-the-stack pins a receipt (revision + dirty fingerprint + service identities, reused shapes) → `environment_down` stops ONLY owned processes.
- Success = first vertical slice ships and proves: 2 services + 1 readiness kind + 1 repo-native E2E + owned-only down, with foreign-listener, crash-orphan, and flaky-readiness acceptance passing; no Compose control, no scheduler, no new dashboard views.

## Decisions
- **Topology: discovery-proposed, chat-approved, workspace-scoped store.** New read-only `environment_propose` derives candidates from existing `discover()` output (`scriptNames`, `composeFiles` presence) plus bounded reads of `Procfile` (up to 20 `name: command` lines, 4 KiB cap) and `Makefile` target names (regex `^[\w:.-]{1,80}$`, max 30) and port hints (regex over script bodies + Procfile: `:(\d{2,5})`, `PORT=(\d{2,5})`, `--port[= ](\d{2,5})`, first valid 1–65535 per service). Compose files are presence-only (existing `composeFiles: string[]`); never parsed or controlled in v1. `Procfile`/`Makefile` are proposal hints only — execution stays on the existing manifest-script path (`package.json` script via fixed `pm2 start npm` argv). A `Procfile` command with no matching `package.json` script proposes as `unmapped — pick the npm script that runs it`, never as an executable command. **Conversational approval rule (binding user decision — no separate approval ceremony):** topology approval is conversational only. The agent calls `environment_propose`, presents candidates in chat, the user confirms in chat ("yes, backend=api/dev on 3000, frontend=web/dev on 5173, frontend depends on backend"), and the agent's subsequent `environment_set`/`up`/`down`/`verify` call IS the record (visible in `activity_list`; no ticket, no modal, no dashboard approve button). MCP role is intent-free for these tools: authority lives in the client permission model plus that explicit in-chat confirmation — no extra intent header, no second ceremony. The dashboard role keeps the standard intent gating (`manage-environment` for set/up/down, `verify-environment` for verify) because dashboard calls bypass chat confirmation. The reviewer already found this approval mechanism sound; this paragraph only removes any separate-ceremony reading. Stored workspace-scoped in `state.json` additive `environments` (max 5 per workspace, max 10 services each, outer entries ≤50 matching the workspace limit — see size arithmetic in Schema/model). Rejected: hand-written manifest file as adoption requirement (friction, drift); auto-executing Procfile bodies (arbitrary shell, breaks the fixed-argv safety construction); any dashboard approval screen or out-of-chat ticket (secondary surface + ceremony friction, deferred by constraint).
- **Readiness v1: two explicit kinds — `http-200` (ready-capable) and `process-alive` (honest non-HTTP kind, never ready). (F1 decision: explicit kind, not http-200-everywhere — keeps honesty for non-HTTP workers such as queue/background workers.)** `http-200`: `GET http://127.0.0.1:<port><path>` expects 200–299 within a per-service bounded poll (interval 1000 ms, default timeout 30 s, allowed 5–120 s); one success marks `ready`; attempts + last status + latency reported. `process-alive`: no HTTP surface; the service's honest ceiling is `starting` (PM2 accepted + still exactly-mapped + alive at poll end) — it is NEVER reported `ready`, and dependents treat its `starting` as satisfied-but-not-ready (recorded distinctly from `ready` so no caller can mistake it for liveness). No `port-listen`-as-ready (port-open ≠ ready per binding direction), no `log-pattern` in v1 (deferred; tails stay diagnostic via existing `service_logs`). Flaky policy = honest attempt log, not consecutive-N gating (rejected as unnecessary for the slice; E2E remains the real verification, readiness stays a liveness gate). Timeout / non-2xx-exhausted / process-exit → `failed` with `lastStatus`; dependents → `skipped` (never started). Start order = topological dependency order, strictly sequential (no parallel starts in v1 — orchestration is ordered owned operations, not a scheduler). `port` is required when and only when `readiness.kind === 'http-200'`; `process-alive` services must set `port: null` and are refused a port probe.
- **Owned teardown: stored owned-set WITH expected root + exact-mapping reconciliation, never kill-by-port/name. (F2 decision: persist `expectedRoot` in each owned entry — not derived from live topology at stop time.)** Each environment record carries `owned: [{ serviceId, pmId, name, namespace, expectedRoot }]` plus `state: down|partial|up`. `expectedRoot` is the canonical `exactRootPath` resolved and validated at start time (inside exactly one workspace root); it is frozen in the owned entry because the topology's `repositoryPath` is user-supplied pre-canonicalization and the topology may be re-`set` between `up` and `down`. Every stop compares BEFORE any runner call: fresh `inspectPm2Services` `exactRootPath === expectedRoot` AND `pmId + name` match AND namespace still matches (mismatch refuses) — this is the recycled-pmId-different-root guard (PM2 reuses pmIds; pmId alone proves nothing). Stale-owned (pmId absent from `jlist`, mapping ambiguous/foreign, or root drift) is cleared WITHOUT any kill and reported `stale/unknown`. `environment_down` iterates reverse dependency order and calls the existing `controlPm2Service`-equivalent path once per owned-and-still-mapped service. Never `pm2 kill`, never port-kill, never name-only match. **Owned-intent persistence ordering (F3):** intent is persisted BEFORE/AT start, not after the readiness poll — phase (a) before spawn stores `{ serviceId, pmId: null, expectedRoot, state: starting }`, phase (b) immediately after the starter returns (before any readiness poll) fills `pmId/name/namespace`, phase (c) after the poll records `ready|failed`. A crash between spawn and phase (b) therefore leaves an intent with `pmId: null` plus a live orphan; the next `up` adopts (never duplicates — see MS2 mid-up crash case). Crash orphans cannot linger past the next `up` and cannot cause foreign kills.
- **Receipt binding: extend `RunSummary`, new `environment_verify` op, receipt size explicitly capped (F4).** The E2E stays repo-native (`npm run <script> --silent`, same 120 s / 64 KiB / `maskSecrets` path as `runVerification`, `src/verify.ts:371-440`). New `environment_verify({ workspaceId, environmentId, repositoryPath, scriptName })` (a) snapshots owned service identities (`pmId/name/namespace/status` via the existing observe-service-link shape) plus per-service repo git context (`revision` + `dirty` fingerprint via existing `observeGitContext`/`observeDirtyFingerprint` shapes), (b) runs the script, (c) persists one `RunSummary` with additive `environment: { envId, envName, services: [{ serviceId, name, pmId, namespace, status, revision, dirty }] }` where receipt `services` ≤10 (inherits the env cap) and per-service receipt `dirty.files` is sliced to ≤10 names (vs 50 in `verify.ts`) with `truncated: true` forced when sliced, so the worst-case receipt stays ≈ 10 × (ids ~100 B + revision 40 B + diffHash 64 B + 10 × 256 B max-length names + status) + envelope < 30 KiB — inside the 64 KiB summary-file budget with the 2 KiB excerpt untouched. If serialization would still exceed 64 KiB, the writer truncates receipt `dirty.files` further (never fails the verification on receipt size; `truncated` records it). Surfaces through existing `recent_runs` / `workstream_context` (excerptPreview, `pinnedByNote`) and existing `recordActivity`; no new dashboard view, no timeline schema fork. Rejected: overloading `verification_run` with N-service context (blurs the proven single-service contract) and stuffing identity into completion-check `environment: string` free text (unstructured, loses fingerprint reuse).
- **Port conflicts: refuse + suggest, never kill.** Before starting each service with a declared `port`, a loopback TCP probe (`net.connect` to `127.0.0.1:port`, 500 ms timeout, no payload) runs. Occupied → that service `failed (port-in-use: <port> is already occupied; not stopped)`, dependents `skipped`, message suggests the first free port in `port+1..port+10` (bounded scan, suggestion only — NO auto-rebind; human changes topology via `environment_set`). No `lsof`-parsing, no kill, no eviction of foreign listeners or foreign PM2 processes.
- **First slice scope (fixed):** 2 fixture services (`backend` + `frontend`, `frontend.dependsOn: [backend]`), both `readiness.kind: 'http-200'` in the slice fixtures (both expose HTTP). The `process-alive` kind ships in schema + unit tests (honest `starting`-ceiling for a non-HTTP worker fixture) but is NOT part of the live-gate E2E path. 1 repo-native E2E script (frontend-repo script that fetches the backend loopback URL and asserts text — still `npm run`, still loopback-only), `environment_down` owned-only proof. Acceptance includes foreign-listener presence, crash-orphan reconciliation (including the mid-up crash case), recycled-pmId-different-root guard, and flaky-readiness honesty (below).
- **Non-goals (with why):** Compose control (read-only `list/logs` today; control needs new trust/volume/network failure semantics and a divergent permission story — deferred, presence-only message explains it); multi-machine / production deploys / auto-scaling (solo-local threat model; M2 leases serialize shared E2E resources instead); generic log streaming (tails stay at existing 200-line / 64 KiB bounds via `service_logs`); any scheduler/cron/queue (ordered operations only; M2 explicitly avoids a premature scheduler per ROADMAP).

## Conditional Surface Contracts
- **Schema/model (store + run summary):**
  ```ts
  // All additive, optional-with-default; strict; unknown shapes fail closed.
  // F1: readiness is an explicit union; 'process-alive' is the honest
  // non-HTTP kind and is NEVER reported 'ready' (ceiling: 'starting').
  EnvironmentReadiness =
    | { kind: 'http-200'; path: string /* 1..256, must start with '/', no whitespace/\0, default '/' */; timeoutSecs: number /* int 5..120, default 30 */ }
    | { kind: 'process-alive' /* no path/port/timeout fields; must set port: null */ }
  EnvironmentService = { id: string /* ^[A-Za-z0-9][A-Za-z0-9:._-]{0,79}$ */; name: string /* PM2 name ^[\w:.-]{1,80}$, defaults to id */; repositoryPath: string /* abs ≤4096, inside exactly one workspace root; stored canonical (realpath) */; scriptName: string /* ^[\w:.-]{1,80}$, must exist in that repo package.json */; port: number | null /* 1..65535, REQUIRED iff readiness.kind==='http-200', MUST be null iff 'process-alive' */; dependsOn: string[] /* service ids, ≤10, acyclic, no self */; readiness: EnvironmentReadiness }
  // F2: owned persists expectedRoot (canonical exactRootPath frozen at start).
  // down/up compare fresh exactRootPath === expectedRoot BEFORE any runner call.
  EnvironmentOwned = { serviceId: string; pmId: number | null /* null = intent persisted before starter returned (F3 phase a) */; name: string; namespace: string | null; expectedRoot: string /* abs ≤4096, canonical */ }
  EnvironmentRecord = { id: string /* uuid */; name: string /* 1..100 */; services: EnvironmentService[] /* 1..10 */; owned: EnvironmentOwned[] /* ≤10 */; state: 'down'|'partial'|'up'; updatedAt: string /* datetime */ }
  State += { environments: Array<{ workspaceId: string /* uuid */; items: EnvironmentRecord[] /* ≤5 */ }> /* ≤50 entries (matches 50-workspace limit), default [] */ }
  // F4: receipt caps — services ≤10, per-service dirty.files ≤10 (truncate + flag).
  RunSummary += { environment?: { envId: string; envName: string /* ≤100 */; services: Array<{ serviceId: string; name: string; pmId: number; namespace: string|null; status: string; revision: string|null /* 40-hex */; dirty: { diffHash: string /* 64-hex */; files: string[] /* ≤10, repo-relative, each ≤256, truncated forced on slice */; truncated: boolean } | null }> /* ≤10 */ } | null }
  ```
  Bounds recap: envs/workspace ≤5, services/env ≤10, outer environment entries ≤50, receipt services ≤10 with ≤10 dirty files each, evidence/run caps unchanged (20-ring/30-pinned, 2 KiB masked excerpt, 64 KiB summary file). **Size arithmetic (F5, max-length paths + realistic ceiling):** transport cap `repositoryPath`/`expectedRoot` ≤4096 each (same `maxProjectRootLength` as registration). Per-service worst case ≈ id 80 + name 80 + repositoryPath 4096 + scriptName 80 + dependsOn 10×80 + readiness path 256 + overhead ~200 ≈ 5.5 KiB; per owned entry worst case ≈ serviceId 80 + name 80 + expectedRoot 4096 + overhead ~50 ≈ 4.3 KiB; per service combined ≈ 10 KiB; per env (10 services) ≈ 100 KiB worst case; per workspace (5 envs) ≈ 500 KiB absolute worst case with every path at 4096 chars. Realistic pilot paths are 30–150 chars, so a realistic per-workspace environments payload is ≈ 5 × 10 × ~300 B ≈ 15 KiB, and current stored states are far below the cap (registrations + workstreams + activity typically single-digit KiB). The 1 MiB `writePrivateJson` guard is the hard ceiling: `environment_set` pre-computes the serialized state size inside `Store.update` and refuses with an allowlisted oversize message leaving the file byte-identical when the write would exceed it (tested with a max-length-root fixture). Stored paths are additionally constrained to canonical resolved paths inside a registered root (length ≤ root length + relative suffix — never an arbitrary 4096-char string), so the worst case is reachable only with adversarial max-length roots, where refusal (not corruption) is the specified behavior. No cap raise, ever.
- **External API/library:** PM2 via existing injected `list/starter/runner` only (no new argv, no `pm2 kill/delete/flush`); readiness via global `fetch` to `http://127.0.0.1:<port><path>` with `AbortSignal.timeout(3000)` per attempt, `redirect: 'manual'` + loopback re-check on redirect (reuse `browser.ts` discipline — non-loopback refused, outside-redirect = failed attempt, never followed); port probe via `node:net` `connect({host:'127.0.0.1',port,timeout:500})`, destroy immediately, no payload; E2E via existing `runBoundedCommand('npm',['run',script,'--silent'],{cwd,timeoutMs:120000,outputLimit:64KiB})`. POSIX-only (`darwin`+`linux`); no Windows branches.
- **Routing (HTTP+MCP, shared ops):** `POST /api/workspaces/:id/environments/propose` (read-only derive, body strict `{}` — roots are the workspace's, never supplied), `POST /api/workspaces/:id/environments/set` (body `{ name, services: EnvironmentService[] }` — full replacement per env name, validated-before-commit, size pre-check before write), `POST /api/workspaces/:id/environments/up` (`{ environmentId }`), `POST .../down` (`{ environmentId }`), `GET .../status?environmentId=` (read-only), `POST /api/workspaces/:id/environment/verify` (`{ environmentId, repositoryPath, scriptName }`, socket timeout 170 s like verify). MCP mirrors: `environment_propose/set/up/down/status/verify` with identical strict zod input; descriptions state owned-only + loopback-only + "Compose is presence-only, not controlled". **Approval/authority split (binding):** MCP calls carry NO intent header — the in-chat user confirmation plus the client's own permission model is the authority, and the mutating call itself (recorded in `activity_list`) is the audit record. Dashboard calls keep standard intent headers (`manage-environment` for set/up/down, `verify-environment` for verify; reads need no intent beyond auth) because they bypass chat confirmation. Every new user-visible error string lives in `environmentMessages` owner const and is appended to `safeMessages` (rename-proof, definition-site-guarded).
- **Persistence/migration:** no migration, no version bump. Old files parse via `.default([])` / `.optional().default(...)`. Writes atomic + 1 MiB-guarded through `Store.update`. `environment_set/up/down` mutate only the matching `{workspaceId, environmentId}` entry; unknown workspace/env → allowlisted not-found; oversized/invalid → refuse with zero bytes changed (test asserts byte-identical file on refusal path). `remove(workspace)` cascades its environments entry (same best-effort runs-dir cleanup pattern).

- **Runtime ownership:** `environment_up` owns exactly the pmIds it started (recorded in `owned` with `expectedRoot`); `down` owns exactly their stops after the root comparison. **Two-phase owned persistence (F3, normative):** (a) BEFORE spawning each service, `store.update` writes the intent `{ serviceId, pmId: null, name, namespace: null, expectedRoot, state: starting }`; (b) IMMEDIATELY after the starter returns (before any port probe of dependents or any readiness poll), `store.update` fills `pmId/namespace`; (c) after the readiness poll, `store.update` records `ready|failed (+ attempts/lastStatus)` or leaves `starting` for `process-alive` services still alive. Steps (a)–(b) are each a single serialized `Store.update`; a crash between them is the mid-up crash case (next `up` adopts — see MS2). Timeouts: list 5 s, start 15 s/service, readiness poll per-service timeout (default 30 s; `process-alive` uses the same window as an aliveness watch, then reports `starting`), E2E 120 s, port probe 500 ms/port (`http-200` services only), suggestion scan ≤10 ports. Caps: proposal reads 4 KiB/file, ≤20 Procfile lines, ≤30 Makefile targets, ≤60 scripts/repo (inherited); log tails unchanged (diagnostic only, never readiness). Cancellation: `up` aborts on first `failed` dependency (dependents skipped); HTTP abort propagates to the in-flight poll via `AbortSignal` (same pattern as verify route); cancellation is not rollback — already-started dependencies stay `starting`/`ready` and are reported, `down` is the explicit cleanup. Adoption rule (normative): when `up` finds a stored intent with `pmId: null` (or stale pmId) AND fresh `jlist` contains exactly one process with `name + exactRootPath === expectedRoot`, `up` adopts that pmId into `owned` and continues its readiness poll instead of starting a duplicate; zero matches → fresh start; ≥2 matches → `failed (ambiguous orphan — resolve manually, nothing started/stopped)`.

## Risks and Rollback
- Risk: `jlist` pmId reuse races (PM2 recycles pmIds) → stale-owned mistaken for live-owned. Mitigation (F2): match on `pmId + name + namespace + fresh exactRootPath === persisted expectedRoot` (never pmId alone); namespace mismatch, root drift, or ambiguity = `stale`, zero runner calls, never touched. Rollback: `down` reports `stale`, next `up` reconciles or adopts per the single-match rule.
- Risk: crash between spawn and owned-fill (F3 mid-up crash) → duplicate start on retry. Mitigation: intent with `pmId: null` exists before spawn; next `up` adopts the single matching live process instead of starting a second; zero matches → fresh start; ≥2 → `failed (ambiguous orphan)`, nothing touched.
- Risk: readiness `fetch` hangs past poll interval. Mitigation: per-attempt 3 s `AbortSignal.timeout`, interval-driven loop capped by per-service timeout; `failed` on exhaustion with `lastError` class only (no body persisted). Rollback: `down` stops started deps in reverse order.
- Risk: port-probe false-negative (probe says free, bind races). Mitigation: probe is advisory preflight; actual bind failure surfaces as service `failed` with PM2/log tail diagnostic (existing `service_logs`), dependents skipped — never retried blindly, never kills occupant.
- Risk: state.json growth (F5). Mitigation: hard caps (5/envs per workspace, 10 services/env, outer entries ≤50) + canonical-path constraint + pre-commit serialized-size refusal leaving the file byte-identical; realistic payload ≈ 15 KiB/workspace; worst-case adversarial max-length paths refuse safely instead of corrupting. No cap raise. Receipt size (F4) is independently capped (≤10 services, ≤10 files each, <30 KiB worst case) inside the 64 KiB summary budget with truncate-never-fail.
- Rollback overall: `environment_down` (owned-only, reverse order, `expectedRoot`-checked, stale-safe) returns the machine to pre-`up` for owned procs; foreign state untouched by construction; topology rollback is `environment_set` with the prior service list (status read confirms `down`).
